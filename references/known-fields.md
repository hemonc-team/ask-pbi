# Журнал подтверждённых находок

Не каталог всей модели — только то, что реально проверено живым DAX-запросом и
пригодилось хотя бы раз. Каждая запись: что искали → что оказалось правдой →
дата/повод. Дописывай сюда, когда ручной DAX-пробник вскрывает что-то
неочевидное, что иначе будешь перепроверять заново каждую сессию.

**С 2026-08-19:** этот файл больше не источник правды для метрик, доступных
LLM — это теперь `mcp_server/registry.py` (+ человекочитаемое зеркало
`references/metrics-registry.md`). Этот журнал остаётся местом для
расследований/находок (почему поле ненадёжно, что показал живой пробник), на
которые ссылаются записи реестра, а не для самих определений метрик.

Формат записи:
```
### <короткий заголовок находки>
- **Датасет/таблица:** ...
- **Оказалось:** ...
- **Как использовать:** ...
- **Найдено:** 2026-08-17, вопрос «...»
```

### ID рекламной кампании ищется по URL, не по utm-полю
- **Датасет/таблица:** `лиды Calltouch✅`
- **Оказалось:** `[utmCampaign]` хранит текстовую метку канала (например
  `"Полиграфия"`), НЕ числовой ID кампании Яндекс.Директа. Числовой ID (например
  `705957657`) находится подстрокой в `[url]` / `[unified_landing_url]`.
  Также встречается в `Директ сводка✅[Кампания Яндекс.Директа]` в формате
  `"master_common ( N-705957657 )"`.
- **Как использовать:** искать кампанию через
  `SEARCH("<ID>", 'лиды Calltouch✅'[unified_landing_url], 1, 0) > 0 || SEARCH(..., [url], ...)`.
  Не пытаться матчить по `utmCampaign` напрямую.
- **Найдено:** 2026-08-17, «анализ кампании 705957657».

### `лиды Calltouch✅[city]` — это гео-бакет таргетинга, не факт. город звонящего
- **Датасет/таблица:** `лиды Calltouch✅[city]`
- **Оказалось:** значения — транслит городов И макро-бакетов одновременно
  (`"moscow"`, `"tver"`, но также `"vse regiony"`, `"centralnye regiony"`,
  `"privolzhe"`, `"jug"`). Это похоже на регион показа объявления/гео-таргетинг
  кампании, а не геолокация звонящего.
- **Как использовать:** если нужен регион лида уровня области — прямого точного
  поля нет; `city` даёт только грубый прокси (конкретный крупный город ИЛИ
  широкий макро-бакет). Явно предупреждать пользователя, что это допущение.
- **Найдено:** 2026-08-17, «конверсия по 5 областям для кампании 705957657»
  (итог: 0 лидов у кампании даже в бакете «centralnye regiony» за оба периода).

### `лиды Calltouch✅[Lifetime Value 1C]` — выручка уже на уровне лида
- **Датасет/таблица:** `leads and bookings managers view` → `лиды Calltouch✅[Lifetime Value 1C]`
- **Оказалось:** поле готовой выручки/LTV пациента, привязанной к конкретной

- **Найдено:** 2026-08-17, «выручка из регионов по кампании 705957657».

### `ОказаниеУслуг` (записи на приём) — в `leads and bookings managers view`, не в `leads_marketing`
- **Датасет:** `leads and bookings managers view` (`39669ce3-7a60-41ee-b465-722d980f155f`,
  workspace `KPI Team`). В `leads_marketing` этой таблицы нет вообще.
- **Оказалось:** таблица приёмов/записей 1С. **Нет прямой связи** к `Лиды✅`/CRM —
  связь только через `Пациент` → `Пациенты[Ссылка]` (GUID), а `ОказаниеУслуг[LEAD]`/`[LEADID]`
  на выборочных строках пустые — не надёжный join к Bitrix-лиду.
- **Как использовать:** если нужна конверсия «лид → запись → приём» по маркетинговому
  каналу/кампании — готового прямого join нет; смотри, не решает ли задачу готовая
  мера (`% Conversion click to booking`, `% Conversion click to visit`,
  `Contact_to_Visit_Conversion_% 1c` — все на грануле `лиды Calltouch✅`/`ОказаниеУслуг`,
  но `Expression` не читается через API — верить с осторожностью, желательно
  свериться с визуалом PBI где эта мера используется).
- **Найдено:** 2026-08-17, «конверсия в запись/приём по кампании 705957657».

### discover-schema падает с INFO.* — известный баг REST API, не проблема доступа
- **Датасет/workspace:** все 3 модели в скоупе `KPI Team` (`KPI marketing view`
  `e6606b8d-...`, `KPI medicine view` `30721258-...`, `KPI team admin view`
  `75e26980-...`) — `discover-schema --scope measures` упал на всех трёх с одинаковой
  ошибкой: HTTP 400, `DatasetExecuteQueriesError`, `AnalysisServicesErrorCode: 3239575574`.
- **Оказалось:** это НЕ доступ/tenant setting (тот даёт 403). `discover-schema` дёргает
  `EVALUATE INFO.TABLES()` / `EVALUATE INFO.MEASURES()` — это подтверждённый внешний
  баг/ограничение классического REST API `executeQueries`: INFO-функции у части
  датасетов (Fabric/Premium capacity) стабильно возвращают именно такую ошибку, даже
  когда обычный DAX (без INFO) через тот же endpoint работает. Подтверждено багрепортом
  в Microsoft Fabric Community: [Unable to use INFO() DAX functions with ExecuteQueries
  REST API](https://community.fabric.microsoft.com/t5/Issues/Bug-Report-Unable-to-use-INFO-DAX-functions-with-ExecuteQueries/idi-p/4383149).
- **Как использовать:** не гонять `discover-schema`/`--refresh-cache` повторно на этих
  датасетах — не починится само. Сначала проверить `execute-dax` с тривиальным
  `EVALUATE ROW("x", 1)` без INFO — если проходит, канал рабочий, просто INFO
  недоступен. Имена таблиц/мер для этих 3 моделей нужно получить вручную (app.powerbi.com
  → панель полей / Analyze in Excel) и вписать в `measures-cheatsheet.md`, дальше
  `execute-dax` с реальным именем меры должен работать напрямую.
- **Найдено:** 2026-08-19, приёмочный тест скилла (KPI Team).

### Естественный вопрос про «конверсию fresh contact за квартал» ловит НЕ ТОТ скилл
- **Оказалось:** в отдельном (не облачном) Cowork-чате с папкой `ask-pbi` активной
  вопрос «Как изменилась конверсия fresh contact за последний квартал по сравнению с

  `conversion-analysis`. Ответ в итоге завершился отказом (запрошен несуществующий
  MCP-коннектор `powerbi-modeling-mcp`).
- **Как использовать:** после правки триггеров (2026-08-19) обязательно нужен
  **повторный** живой тест этого же вопроса в локальном Cowork-чате — убедиться, что

### ⚠️ ОПРОВЕРЖЕНИЕ (2026-08-19, вечер): `discover-schema` починили — прошлые выводы «мера не фильтруется по дате» были ошибкой методики, не свойством модели

- **Что изменилось:** маркетолог выдал право **Build** на уровне датасета (Manage
  permissions → Прямой доступ → галочка «Создание»). Классические `INFO.TABLES()`/
  `INFO.MEASURES()` всё равно падают той же ошибкой (`AnalysisServicesErrorCode
  3239575574`) даже после этого и после полностью чистого device-code входа — но
  рабочей заменой оказался **новый синтаксис `INFO.VIEW.TABLES()`/`INFO.VIEW.MEASURES()`/
  `INFO.VIEW.COLUMNS()`/`INFO.VIEW.RELATIONSHIPS()`** — эти отработали сразу и вернули
  полную схему (66 мер в `KPI marketing view`, 163 в `KPI team admin view`, 67 в
  `KPI medicine view`). `scripts/pbi_service_client.py.discover_schema` переведён на
  `INFO.VIEW.*`.
- **Что это меняет:** более ранний вывод «`[Количество свежих контактов]` не реагирует
  на фильтр по дате» был правдой на момент написания, но сам вывод «мера
  снепшот/сломана» оказался **ошибкой методики проверки**, не фактом о модели.
  Настоящая причина: таблица `Лиды✅` (где живут обе меры) не имеет активной связи с
  `Date_dim` вообще — фильтр по `Date_dim[Date]` физически ни на что не действовал,
  поэтому результат совпадал что с фильтром, что без. Активная связь идёт по цепочке
  `Лиды✅` ↔ `crm_lead_uf✅`[DATE_CREATE YearMonth] → `date_dim_month`[YearMonth] — то
  есть фильтровать нужно **`date_dim_month[YearMonth]`**, гранулярность — календарный
  месяц (дневной таблицы для этой цепочки нет).
- **Подтверждено живым запросом:** `[Количество свежих контактов]` по
  `date_dim_month[YearMonth]` даёт нормальные помесячные значения (2026-06=509,
  2026-07=574 в `KPI marketing view`) и корректно суммируется по кварталу (Q2
  2026=1584=577+498+509). `[Fresh_Contact_Conversion_Rate_%]` по одному месяцу даёт
  разумный % (2026-06≈51.08), но при фильтре на диапазон из >1 месяца (квартал,
  `Year=2026 && Quarter="Q2"`) возвращает **пусто**, а не число — отдельная реальная
  особенность самой меры (похоже на `HASONEVALUE`-проверку внутри), не баг клиента.
- **Также нашли:** мера `Contact_to_Visit_Conversion_% 1c` (таблица `ОказаниеУслуг`,
  видна на скриншоте пользователя как «Конверсия первичных контактов в состоявшийся
  приём») существует и в `KPI marketing view` тоже (не только в заблокированной модели,
  как считалось раньше) — активная связь `ОказаниеУслуг[ДатаОказанияУслуг] →
  date_dim_daily[Date]`, дневная гранулярность. Более точное совпадение с графиком
  пользователя — мера `Conversion_Primary_Booking_to_Visit_% 1c` (65-82% за 2021-2026,
  тоже через `date_dim_daily`).
- **Как использовать:** реестр метрик (`mcp_server/registry.py`,
  `references/metrics-registry.md`) переписан с этими тремя подтверждёнными метриками.
  Не считать более старые записи про Date_dim/снепшот руководством к действию — они
  оставлены только как история расследования, актуальную картину см. в
  `metrics-registry.md`.
- **Найдено:** 2026-08-19, вечер, после выдачи Build permission пользователем.
